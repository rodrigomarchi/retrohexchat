# Virtual-space scenes, spaces & maps — pipeline & playbook

How a virtual-space map is designed, generated (PixelLab), composed, authored,
and wired into the app. Read this before creating or reworking a scene. Like
[`CHARACTERS.md`](CHARACTERS.md), most of this is hard-won empirical knowledge.

The worked example throughout is the **End of Time** — the cozy two-person
"stone island adrift in a starry void" scene behind every private conversation.

---

## 1. What a scene is

A scene is a **map definition** consumed by the client renderer. A map module
(`apps/retro_hex_chat/lib/retro_hex_chat/virtual_space/maps/<name>.ex`) exposes
`definition/0` returning:

| Field | Meaning |
|---|---|
| `id` | Registry key (must match). |
| `width`,`height`,`tile_size` | In tiles; `tile_size` is always **32**. World `scale` is always **1** and `avatar_scale` is always **1** — one resolution, no derived scaling. |
| `tilesets` | `[%{id, src: "/images/space/<id>.webp", tile: tile_size, columns}]` — sheets the client loads. **`tile` must equal `tile_size`** (the atlas slices by it). |
| `tiles` | `name => %{ts, col, row, w, h, flip_x?, frames?, period_ms?}` — the vocabulary (rects on a sheet). Must contain `ground`. |
| `ground` | Opaque base tile drawn under every floor cell (the void terrain tile, e.g. `f0000`). |
| `layers` | `%{floor: HxW matrix of tile names, decor: [%{x,y,tile,sort}], above: []}`. `sort:"flat"` (starfield, under everyone) vs `"stand"` (props Y-sorted with avatars → walk-behind). |
| `lights`,`ambient` | Color-math atmosphere: additive radial `lights:[{x,y,radius,color,blend}]` and a multiply `ambient:{color,alpha}` dusk wash. Absent → scene renders full-bright. |
| `spawn` | `[%{x,y,dir}]` — off-collision, in-bounds. |
| `collision` | `[%{x,y,w,h,kind}]` → expanded to a blocked-tile set. |
| `zones`,`labels`,`interactables`,`seats` | Metadata + interactive furniture. |

**Render order** (`renderer.js draw()`): void backdrop → sea →
floor → **flat decor** (starfield) → **shadows** → **depth pass** (`stand` decor
+ avatars Y-sorted together, so avatars walk **behind** taller props) → `above`
layer → **color-math lighting** (ambient multiply wash + additive light pools) →
map labels → the **focus prompt** → nick labels/bubbles. The target the use
button reaches (`focus.js`) is ringed in gold as the depth pass draws it. So:
- **Walk-behind works:** a `sort:"stand"` prop occludes an avatar while the avatar
  is above its base row, and the avatar passes in front once past it. `sort:"flat"`
  decor (stars) stays under everyone. The `above` layer draws over all avatars.
- **Atmosphere is color-math, not baked art:** the amber lamp pool, cyan Gate glow
  and cozy dusk tint are canvas `globalCompositeOperation` passes driven by the
  map's `lights`/`ambient`. Motion is
  still real frames (stars) — no procedural animation in the art.
- The renderer is **size-agnostic**; multi-tile decor is anchored **top-left**
  and drawn at native sprite size. `flip_x` mirrors without moving the anchor.

Maps are authored **layout-only** (tile names + positions, no pixels); the
client slices the sheets at runtime. Big/complex layouts are generated by a
Python tool that writes JSON to `priv/maps/<name>.json`, and the module loads it
(see `EndOfTime`, the scene behind every channel and DM, and `Construct`, the
buildable room behind its gate — §10).

## 2. Generating scene art (PixelLab MCP)

The scene is **isometric** (a flat diamond floor + a floating 3D slab). Check
`mcp__pixellab__get_balance` first. The full iso art pipeline — the inviolable
aspect-ratio rule, why `create_map_object` at an exact flat canvas beats
`create_tiles_pro`, the sheared railing tiles, the procedural sea — lives in
[`ISOMETRIC.md`](ISOMETRIC.md) §4. The essentials:

### 2a. Floor diamond — `create_map_object` at an exact flat canvas

The flat cobblestone diamond is a single `create_map_object` at an **exact
flat-2:1-class** canvas ("diamond … fills the entire rhombus"): transparent
corners + a filled centre that **tessellates seam-free**. The shipped floor
variations (`iso/floor_0..3.png`) are **48×20 native**; the projection reads
`iso.tile_w/tile_h` from the art's own size, so whatever exact canvas you
generate at is the diamond the engine tessellates (the original 64×32
calibration also worked). `create_tiles_pro` isometric only yields ~1:1 diamonds
(too steep for the flat CT look) and ignores `tile_height`, so it is NOT used
for the floor. The author must **never crop or resize** the floor tile — the
exact native canvas must survive or tessellation seams appear.

### 2b. Props — `create_map_object` as iso billboards

Standalone transparent-background objects, ~15–30s each. Upright props (e.g.
lamp, pillar, signpost) are drawn as **iso billboards** — an upright object
reads correctly in any projection, bottom-centred on the diamond foot, so no
iso-specific art is needed:

```
outline: "single color outline"
shading: "basic shading"
detail:  "medium detail"
```

Railings are NOT generated — they are drawn **geometrically** along the platform
edges (see [`ISOMETRIC.md`](ISOMETRIC.md) §3); a baked fence sprite can never
match the 2:1 edge slope.

**Rate limits:** ~4–5 objects in flight before `rate limit exceeded` — wait
~15–30s and retry. Download: `curl -L /mcp/map-objects/<id>/download` (returns
the full requested canvas with transparent padding).

Calibrate ONE floor tile + ONE prop, eyeball them, then batch the rest.

## 3. Composition

### The floor — a few tessellating diamond variations

The iso floor is a small set of same-size diamond variations (currently 4,
`iso_floor0..3`, hash-picked per cell) — no Wang autotiling, no corner LUT. The
tiles' transparent corners let neighbours interlock seam-free. Cells off the
platform carry no floor (the `ground`/void tile is skipped so the slab floats).
The starry sky's *life* comes from scattered **animated star tiles** — see
[`ANIMATIONS.md`](ANIMATIONS.md) (currently the script-drawn `iso_star`).

### The shape → floor matrix

The platform is a **straight-edged** rectangle (or bevelled octagon) in tile
space — never an organic super-ellipse, which would make the geometric edge
railings staircase (see [`ISOMETRIC.md`](ISOMETRIC.md) §3). The floor matrix stays
a plain square H×W grid; solid cells get the floor diamond, the rest are void.

### The packed sheet

`author_scene.py` packs everything into one 32px sheet
(`priv/static/images/space/<name>.webp`): the floor variations (packed at their
native size, recorded as `wpx/hpx`, **never cropped**) + the sheared railing
tiles and post + the static props (each **bottom-center anchored** in its `w×h`
tile block) + any **animated tiles** as horizontal frame strips (see
[`ANIMATIONS.md`](ANIMATIONS.md) for the packing rules — union bbox,
scale-to-fit; the current scene's only strip is the script-drawn `iso_star`).
It emits the tile **vocab** (`name → {col,row,w,h,wpx?,hpx?,frames?,
period_ms?,flip_x?}`) plus the full layout into `priv/maps/<name>.json`:
`floor`, `decor` (painter order: stars, then props), `collision` (off-platform
void cells — block solid prop footprints too when adding furniture; the current
scene blocks none), `spawn`, `zones`, `labels`, and the iso `slabs`/`railings`
geometry.

> **No runtime procedural animation on the platform.** There is no baked glow or
> runtime-drawn motion; movement is frames baked in the sheet, cycled by the
> engine ([`ANIMATIONS.md`](ANIMATIONS.md)). Exceptions today: the procedural
> sea/void behind the floating slab ([`ISOMETRIC.md`](ISOMETRIC.md) §2) and the
> `iso_star` frames, drawn by the author script at build time (a stopgap — see
> the status note atop `ANIMATIONS.md`).

Raw art lives in `virtual.space/scenes/<name>/`; the tool reads it and is
deterministic — re-run after regenerating any art.

## 4. The map module + integration

The Elixir module is thin — it declares its own `tilesets` (self-contained
sheet), turns the JSON `vocab` into `tiles`, and passes the rest through:

```elixir
%{id: "end_of_time", ..., tile_size: data["tile_size"],
  tilesets: [%{id: @sheet, src: "/images/space/#{@sheet}.webp", tile: 32, columns: data["columns"]}],
  tiles: Map.new(data["vocab"], fn {n,v} -> {n, %{ts: @sheet, col: v["col"], row: v["row"], w: v["w"], h: v["h"]}} end),
  ground: data["ground"], layers: %{floor: data["floor"], decor: ..., above: []}, ...}
```

Wire it up:
1. Drop the sheet in `apps/retro_hex_chat_web/priv/static/images/space/` (Phoenix
   serves it automatically) and the JSON in `apps/retro_hex_chat/priv/maps/`.
2. Register the module in `virtual_space/map.ex` `@maps`.
3. Point whoever uses it — the DM space is chosen at
   `channel_space_server.ex` `SpaceMap.get("end_of_time")`.
4. Keep a `%{id: "dm_nameplate", kind: ...}` label if it's a DM scene — the
   server fills it with `"nickA + nickB"`. End of Time uses the `hologram` kind
   (glowing text on the artifact); see §7.

## 5. Add a new scene — checklist

1. **Design** it (prose + ASCII) and agree on the vibe before generating.
2. **Generate** (§2): calibrate a floor tile + a prop, then batch. Save raw art to
   `virtual.space/scenes/<name>/`.
3. **Author** (§3): extend/copy `author_scene.py` — platform shape, packing, layout,
   slabs/railing geometry. It writes the sheet + `priv/maps/<name>.json`. Eyeball
   it via the Playwright screenshot (`e2e/test-results/end-of-time.png`, see §5
   of [`ISOMETRIC.md`](ISOMETRIC.md)).
4. **Module** (§4): a thin `Maps.<Name>` loading the JSON; register in `map.ex`;
   point the consumer.
5. **Tests**: add the id to `map_test.exs` `@map_ids`; update any consumer test
   asserting the map's `id`/`width`/`height` (`space_channel_test.exs`,
   `direct_message_space_test.exs`).
6. **Validate**: `make ci` (9/9) — `map_test` enforces spawns off-collision,
   floor-matrix integrity, and known tiles. Then Playwright-verify in a browser
   (`e2e/tests/space-end-of-time.spec.ts` drives a real PM into the scene).

## 6. Gotchas, distilled

- **Straight platform edges** (rect/octagon), never a super-ellipse — else the
  geometric railings staircase ([`ISOMETRIC.md`](ISOMETRIC.md) §3).
- **The floor tiles are native-size diamonds (currently 48×20), never
  cropped/resized** — a cropped tile breaks seam-free tessellation; the
  projection reads the diamond ratio from the art.
- **Void life comes from animated star tiles** — hash-scatter animated stars
  over the void for a twinkling sky ([`ANIMATIONS.md`](ANIMATIONS.md)); the sea
  behind the slab is procedural ([`ISOMETRIC.md`](ISOMETRIC.md) §2).
- **Upright props are iso billboards** — bottom-center them in their tile block so
  the base sits on the diamond foot; railings are geometry, not sprites.
- **Depth is real:** `sort:"stand"` decor Y-sorts with avatars (walk-behind),
  `sort:"flat"` stays under everyone, and the `above` layer draws over all. Tag
  every decor entry's `sort` in the author script (starfield = flat, props = stand).
- **Collision is the complement** — block every non-full-stone cell (the void)
  plus solid prop footprints; keep spawns on interior stone, clear of props.
- **A DM scene keeps the `dm_nameplate` label** so the server nameplate works.
- **Swapping the map** breaks id/size assertions in `space_channel_test.exs`
  and `direct_message_space_test.exs` — update them.
- **Playwright: a PM must be activated** (`getByTestId('pm-<nick>')`), `/msg`
  alone opens the tab but doesn't focus it; a PM's topic bar shows no nick.

## 7. Decorating props — patterns from the End of Time set

- **Facing pairs: 8-direction rotations beat `flip_x`.** For two DIFFERENT
  characters facing each other (the Matrix nook), generate each as a
  `create_8_direction_object` and use the opposing rotations (`east` seated
  profile for the west seat, `west` for the east seat) — prompts alone won't
  turn a seated composition, and each side keeps its own identity. `flip_x`
  (two vocab entries on one rect, the second mirrored) still serves identical
  props; the Elixir `tiles/0` must copy `flip_x` onto the rect.
- **Dynamic text on a prop → the `hologram` label**, the only label kind the
  renderer draws: a plaque won't sit inside a stone/tech artifact. The `hologram` label kind (in `renderer.js`) draws glowing cyan text
  with a 1px glow and **no frame of its own** — it floats on the prop's own
  display panel. Give the label a `w` matching the panel; `fillText`'s maxWidth
  shrinks long nicks so they never spill past the artifact.
- **Place the display, then the text** — measure where a prop's screen panel
  sits (script a scan of the packed sheet for the bright/coloured band), then
  set the label's x/y/w to land the text on it. A prop is drawn from its
  top-left, so a tall prop placed too high gets its top (and any banner)
  clipped by the viewport — lower it until the panel is comfortably in view.
- **Props can overhang the void** — decor is drawn regardless of the floor, so a
  monument's top may rise off the island into the starfield (dramatic); only its
  base needs to sit on walkable stone (block that footprint).

## 8. Art-style COHESION (32px iso)

`create_map_object` at `high detail` on a large canvas produces beautiful but
**illustration-scale** sprites that read as *stickers pasted on the floor*. A
cohesive JRPG/Chrono-Trigger scene needs the floor, the props and the **avatar**
all at the **same pixel density and palette register**. Map-agnostic rules:

- **Generate props NATIVE.** Generate each prop at (roughly) its **native on-map
  pixel size** — set its tile size to `ceil(content_bbox / 32)` so the packer
  neither up- nor down-scales it (crisp pixels that match the 32px iso tiles).
  Keep `outline`, `shading` and `detail` identical across every prop so they
  share one register.
- **Judge cohesion against the AVATAR, not in isolation.** A prop can look great
  alone and still clash with the character. Calibrate 2-3 props, render them
  **next to the actual avatar sprite** (a frame of a character from
  `creator_contact_sheet.py`), confirm the style, THEN batch-regenerate everything. Cost of skipping
  this: regenerating everything twice.
- **Curate, don't mirror-stamp.** Auto-mirroring the same lamp/bench N times to
  fill space reads as repetitive/lazy. Hand-place a varied set — each piece with
  a reason and a spot — asymmetric but balanced.

### Validate the layout programmatically (before trusting a browser)

The author script's determinism lets you assert the layout in a few lines —
do this every rebuild:
- **Prop overlaps**: pairwise bbox test over `decor` using the vocab `w/h`.
- **Spawns off collision**, on the walkable platform (not overhanging the void).
- **Greedy-walk reachability**: `space_channel_test` walks with a greedy
  **X-then-Y** stepper, and `input` returns `{:error, :blocked}` on a blocked
  tile — so the *entire* path from `spawn[0]` to each target tile must be
  collision-free. Simulate that greedy walk in Python against the collision set
  and pick spawn/approach tiles so it never snags (a prop's base row across a
  corridor will stall it).
- **Animated frames on-sheet**: every frame cell of each animated tile must be
  non-empty (see `ANIMATIONS.md` — widen `SHEET_COLS`, and keep a guard).

> **Seats/zones/boards need a map that defines them.** End of Time is a
> bare walkable cross of platforms — it declares no seats or interactive boards
> (zones only name the five platforms), so channels render it as open floor.
> Tests that exercise seat/zone/board logic
> inject their own **fixture map**; they are not coupled to End of Time's coords.

## 9. Isometric projection (End of Time)

> **Full playbook: [`ISOMETRIC.md`](ISOMETRIC.md)** — the durable, hard-won guide to
> building isometric 3D scenes (projection seam, geometric railings, the floating
> slab/diamond underside, procedural sea, the iso art pipeline + aspect-ratio rule,
> depth ordering, all the gotchas). Read it before any iso work. The summary below
> is the cross-reference.

**Isometric is the only projection.** `assets/js/lib/space/projection.js` exposes a
single `IsoProjection`; `createProjection` always returns it. The whole difference
from a naive square grid is a **projection seam** — the tile→pixel mapping, depth
order, hit-test inverse and input remap — injected into Camera/Renderer/Engine.
**Movement, collision, spawns and the server stay a square (x,y) grid** — the
diamond is *purely* a rendering projection of that grid. `worldToScreen` (camera
offset) is untouched.

Iso map fields:

| Field | Meaning |
|---|---|
| `iso: {tile_w, tile_h, z_step, headroom}` | diamond footprint (the art's native size, currently 48×20) + elevation px |
| `slabs: [{thickness,taper,hull}]` | one 3D block per platform/bridge → the floating slabs |
| `vignette: {color, alpha, inner}` | screen-space radial multiply framing the void |
| `layers.decor` `sort:"stand"` | props/railings billboard on the diamond foot, depth-sorted by `x+y` |

Hard-won iso lessons:
- **Ratio is native, never deformed.** `create_tiles_pro` isometric yields ~1:1
  diamonds (too steep for CT's flat look) and ignores `tile_height`. The reliable
  flat cobblestone diamond came from **`create_map_object` at an exact flat
  canvas** (transparent corners → tessellates seam-free; shipped floors are
  48×20 native, and the projection reads the ratio from the art). The author
  must NOT crop the floor tile.
- **Iso floor** is drawn far→near (`x+y`), skipping the `ground`/void tile so the slab
  floats; **slab faces** are dark extruded quads on boundary tiles.
- **Railings** are drawn **geometrically** along the platform edges — a continuous
  contour on the exact diamond-edge endpoints, not billboard sprites (a baked slope
  never matches the 2:1 edge). See [`ISOMETRIC.md`](ISOMETRIC.md) §3.
- **Reuse** upright props (the lamp today) as iso billboards — bottom-centre on the
  diamond foot; an upright object reads correctly in any projection.
- Depth is keyed by `projection.depthKey` (base tile `x+y`, height a tie-break) so
  back-edge railings draw behind whatever stands on their cell (avatars, a
  gate put against the rail), front-edge in front; ISOMETRIC.md §3 has the
  numbers and the posts.

## 10. The Construct (a buildable room)

The **Construct** is the second registered map: an empty white floor behind the
End of Time's green gate (`eot_portal`, at (45,28) against the centre platform's north railing, interactable
`construct_portal`), where the people of a channel or DM place furniture. Its
author is `virtual.space/tools/author_construct.py`, which writes
`construct.webp` and `priv/maps/construct.json`.

- **It floats in the End of Time's sky**: a 48×48 floor inside an 8-cell
  margin of void, under the same sea, stars and vignette (values copied from
  `author_scene.py`) and one slab; no ambient wash, so the floor stays white.
- **The floor is drawn, not generated**: the End of Time floor's own 48×20
  alpha, filled white with a grey seam, so it is exactly the diamond the
  projection tessellates — and the seam is the grid builders place on.
- **Pieces are PixelLab map objects** (`virtual.space/scenes/construct/`):
  furniture (chair, armchair, table, bookshelf, lamp, tree, plant), structure
  (wall, door and its `door_open` state from `create_object_state`) and the
  pieces that do something (teleporter, die, coin, sign, arcade cabinet,
  board, screen), plus the white exit gate. Generated native at single-colour
  outline / basic shading / medium detail and judged next to an avatar frame
  before the batch; ask for the object "standing alone", or PixelLab adds a
  stool to the door and a chair to the bookshelf. Each art is tile `down` as
  drawn and its `flip_x` twin is tile `right`; which way that faces is the
  art's own — a bookshelf shows its front down-left, a cabinet or any seat
  down-right (§11, "Facing").
- **The library** (`LIBRARY` in the author) adds a tab per theme — office,
  garden, gamer, beside the home furniture — each kind one PixelLab object
  named `<kind>.png`. A piece longer than a tile declares its `size`
  (`[w, h]` tiles, the long side down the y axis, which is how PixelLab draws
  "running from bottom-left to top-right"); a sofa or a bench lists its
  `seats`. Its art stands, unless `foot` says otherwise, brought forward of
  the footprint's centre until its lowest pixel is just short of the
  footprint's front corner — it is drawn with the floor it covers, and stood
  on the centre it floats over its tiles — except a piece with `seats`, which
  stands on its centre so the seat is under whoever sits on it (drawn there,
  raised by the renderer's seat lift). Where it falls among the people around
  it stays its footprint's centre: the decor carries that as `depth`, which
  the renderer sorts by. A sofa's art reaches about a tile behind its seats:
  keep it off the platform's edge. Generate a long piece on a wide canvas (≈112 px for two tiles)
  and say it "fills the canvas", or it comes back the size of a stool.
- **Art already in the PixelLab account is fetched, not regenerated.** The
  fair and fantasy tabs, the Victorian pieces and a few more are objects made
  for scenes that never shipped. `scenes/construct/pixellab.json` names each
  piece's PixelLab object (and animation), and
  `tools/fetch_pixellab_objects.py` downloads them into the layout below, so a
  piece can be traced back to where it was drawn. An entry is an `object`
  (with its `animation`), a `map_object`, or an `image_job` (an
  `animate_image` run over a map object, frame 0 being the still). A loop is
  made of the generated frames alone (`first: 1`): the still is drawn with a
  smaller palette than the frames after it, and shows as a flicker once a
  loop. A map object may not outlive its day on PixelLab's side, so its id
  records where the art came from; the committed PNG is the art.
- **Scale: size a piece against a person before generating it.** A character
  stands ~90 px tall, about 1.75 m, so **1 m ≈ 51 px** of drawn height. Pick the
  object's height in metres from the table, multiply, and generate on a canvas
  whose height is that plus ~10%; the art must fill it. The footprint follows
  the drawn width: an n×m piece's diamond is `(n + m) × 24` px wide, so take the
  smallest footprint that is at least as wide as the art (trees are the
  exception: they block their trunk's tile and their crown overhangs, so 1×1).
  The drawn height includes the floor diamond the piece stands on, about 20 px
  a tile of depth, so a big footprint measures taller than the object stands.
  The canvases below are typical, not exact: what matters is the drawn height.
  `scripts/tests/test_construct_scale.py` measures the packed sheet and fails a
  piece that drifts out of its band.

  | Kind of object | Height | px | Canvas (w×h) | Footprint |
  |---|---|---|---|---|
  | Bucket, small pot, CRT on the floor | 0.4–0.8 m | 20–45 | 32×32 – 48×48 | 1×1 |
  | Chair, bench, crates, planter, hedge | 0.8–1.1 m | 40–60 | 64×56 | 1×1 |
  | Table, counter, stove, altar | 0.8–1.1 m (+ depth) | 50–80 | 64×64 – 112×96 | 1×1 – 1×2 |
  | Wardrobe, fridge, rack, board, signpost | 1.8–2.0 m | 90–110 | 56×112 – 96×120 | 1×1 |
  | Market stall, arcade, vending machine | 2.0–2.4 m | 100–120 | 112×128 – 128×128 | 2×2 – 2×3 |
  | Small tent | 2.5–3.0 m | 125–150 | 128×160 | 2×2 |
  | Lamppost, flagpole, column | 3.0 m | 150–160 | 40×160 – 48×160 | 1×1 |
  | Tree, pine, palm | 3.0–3.5 m | 160–180 | 128×192 – 128×208 | 1×1 |
  | Fair arch, bell tower, temple gate | 3.0–3.6 m | 140–185 | 144×176 – 192×208 | 1×4, 2×2, 3×3 |
  | Big top, fortune-teller's tent | 3.2–3.5 m | 165–175 | 160×176 – 176×192 | 3×3 |

  What the account's credits taught, so the next piece is right first time:
  - **Say it fills the canvas, and mean it**: "fills the whole canvas from edge
    to edge" or "reaching from the bottom to the top of the canvas". Without it
    PixelLab draws the object at about two thirds of the canvas, or smaller.
  - **Name the size against a person** ("as tall as a grown man", "twice as
    tall as a man", "knee-high"). It keeps a tent from coming back stool-sized.
  - **Thin objects shrink.** A string of bunting came back 44 px tall on a
    112 px canvas until the prompt said its posts reach the top of the canvas;
    give a pole or a string a canvas just wide enough for it.
  - **Very large canvases can lose the transparency.** The big top came back on
    an opaque light backdrop twice at 208×224 and came back clean at 176×192;
    the temple gate came back clean at 192×208. Check alpha before anything
    else, and stay at or under ~192×208.
  - **Measure, don't eyeball**: crop to the drawn pixels and compare the
    height with an avatar frame; compare the lowest pixel of the left and right
    quarters for the diagonal (right end higher, or `mirror`).
  - **Animate after the still is approved**, with `animate_image` on the map
    object, and loop on the generated frames (`first: 1`). A large frame costs
    more (a 144×192 animation is 3 generations) and its strip needs room on
    the sheet: `SHEET_COLS` is 40, so a 6-frame strip may be 6 cells wide.
- **Judge the drawing's direction, not PixelLab's `view` label.** Every piece
  runs from bottom-left to top-right or is round; old objects drawn straight
  at the camera (a gate, an arch, a sign board) block a diagonal of tiles while
  their picture runs across the screen. Regenerate them with `create_map_object`
  and say where each end stands: "the left post lower and nearer at
  bottom-left, the right post higher and further away at top-right" turned a
  frontal fair arch into a diagonal one where "isometric 3/4 view" alone did
  not. Art drawn along the other diagonal is turned with `mirror`. Before taking one, judge its
  size against the existing pieces (a chair stands ~57 px, a fridge ~99): the
  account's "16-bit JRPG" set is drawn at 32 px and looks like dolls' furniture
  in a room.
- **A piece that moves** is a directory of frames, `anim/<kind>/<i>.png`
  (`"anim": True` and a `period_ms` in `LIBRARY`). The author crops every frame
  to the box that holds them all, so the piece stands still while what moves in
  it moves, and packs them side by side as one tile with `frames` — the same
  strip the End of Time's sheet uses, which the atlas already steps through. A
  frame with no transparent pixel is refused: PixelLab sometimes returns a
  solid grey block as the last frames of an animation; `pixellab.json` then
  names fewer `frames` and says why.
- **The End of Time's pieces are the End of Time's own art**: their vocab
  entries point at the `endoftime` sheet (`ts`), which the Construct lists as
  its second tileset, so nothing is copied. Each `foot` is the anchor the
  sprite was authored on in `author_scene.py`, and the Balrog's flames are a
  `layers` entry drawn on the same point.
- **Variants that are the same art are drawn, not generated**: the lamp
  switched off (its bright shade dimmed), the coin's silver side (its gold
  recoloured, mirrored), and the four wall corners, each two halves of the
  wall meeting at the tile's centre.
- **The floor is one character per tile** (`w` white, `g` the void, a digit
  per paint material), so a row is a string; the painted diamonds reuse the
  white floor's alpha and seam.
- **The JSON carries four fields only this scene has**: `catalog` (kind →
  tiles per facing, and optionally `seat`, `lights`, `blocks`, `dirs`, `use`,
  `states`, `only`, `group`, `label`), `reserved` (the gate, its apron and the
  spawns — never buildable), `materials` (the floor paints) and `max_items`.
  What was built is not in the file: it is `virtual_space_constructs` in the
  database (pieces and painted floor), merged onto the base by
  `VirtualSpace.Construct.Layout.apply/3`.
- **Adding a kind**: generate the art (or name an existing object in
  `pixellab.json` and fetch it), add it to `LIBRARY` in the author, re-run
  it, add it to its tab in the palette component and its label to the
  glossary. A kind that does something on E names its `use`, which
  `Construct.Layout.use/5` has to know.

## 11. The Office (a furnished buildable room)

The **Office** is a registered map of its own: the Construct's platform with
furniture already in it, behind the wooden door beside the green gate, both
against the centre platform's north railing (`eot_office_door` at (42,28),
interactable
`office_portal`, action `enter_office`). Its author is
`virtual.space/tools/author_office.py`, which writes `priv/maps/office.json`.

- **It adds no art of its own.** It copies the Construct's `catalog`, `vocab`,
  `tilesets` and `materials` out of `construct.json`, so every piece of the
  Construct can be placed in it and its furniture is drawn from the same
  sheets. The End of Time's door is the Construct's `door.png`, mirrored the
  way `author_construct.py` turns it, packed into `endoftime.webp` by
  `author_scene.py`. Order matters: `author_scene.py`, then
  `author_construct.py` (it copies the End of Time's vocab), then
  `author_office.py`.
- **A 24×20 floor in an 8-tile margin of sky**, painted from the start (grey
  stone, blue carpet under the desks and in the meeting room, wood at the
  reception, checkerboard in the kitchenette). Painting it again works as in
  the Construct; Erase brings back the white floor.
- **The furniture is `fixed_items`**: catalog pieces with ids `fixed:<n>`,
  placed like anybody's (`x, y` the footprint's back corner, `dir`). The
  runtime draws them, seats people on their chairs and switches their lamps
  through the same `Construct.Layout` code as any piece, and refuses to move,
  turn, remove or relabel one (`:fixed`); storage keeps only what they are
  doing (a lamp off), never where they are. The client never picks one up.
- **No wall stands on the platform's edge**: the floor's edge is the room's.
  The rooms inside it are walled in **panes** drawn by the author, not
  generated (`_pane`): `glass_wall`, `glass_door` (its open state the frame
  alone) and `cubicle_partition`. A pane stands on one **edge** of its tile,
  on the floor's own slope (24 px across, 10 up), so the far end of one is the
  near end of the next and a run reads as one wall; its facing names the edge
  ("down" +u, "up" -u, "right" +v, "left" -v) and the catalog's `feet` the
  point it stands on for each. The pane's tile is blocked — outside the room
  it walls, a strip along the outside of each run, except where two rooms
  share a wall and one gives up a column — so the room's floor is its inner
  tiles and stops at the glass; it sorts just behind its edge (`depth`); two
  runs meet at a point, with no corner piece. The way out is the wooden door
  standing at the edge (`office_exit`, `exit_office`), with the tile in front
  of it and the spawns `reserved`.
- **Facing**, in three cases. A bulky one-tile piece faces the way its art
  was drawn, which is not the same for every kind: the bookshelf, the vending
  machine and the fridge show their front as "down" (+v); the file cabinet,
  the printer, the coffee machine and every seat show theirs as "down" toward
  +u, and as "right" toward +v. Look at the art before placing one against an
  edge. Whoever sits faces the way the seat's art opens (`SEAT_FACING` in the
  renderer: "down" down-right, "right" down-left). A two-tile piece runs down v
  as "down", facing +u, and across u as "right", facing +v. A flat board (the
  whiteboard, the screen) runs down v as "down", facing +u, so along the back
  edge at `v = 0` it is "right".
  Somebody at a `workstation` sits behind it, facing the room, its monitor's
  back to the viewer — every chair faces the viewer, so a desk whose sitter
  would face away cannot be furnished.
- **A door is a way through**: the trap check (`Construct.Layout`) never counts
  a door as a wall, open or shut, since whoever is behind it opens it with E;
  so a closed glass door with somebody behind it holds up no edit.
- **The author checks the plan before writing it**: every piece on the floor
  and off the reserved tiles, none overlapping, every free tile reachable from
  the door (through the glass doors) and every chair reachable to sit in
  (`scripts/tests/test_office_authoring.py` runs the same check).
- **Its own pieces** live in the Construct's `office` tab. Generated for it:
  `reception_desk` (1×2), `trash_bin`, `tall_plant` and `workstation` (1×2,
  its near-side keyboard recoloured away in the PixelLab workbench, as
  `pixellab.json` records). Drawn by the author: `glass_wall`, `glass_door`
  and `cubicle_partition`. All are sized against a person by the table in §10
  and held to it by `test_construct_scale.py`.
- **Moving the furniture is editing `FURNITURE`** in the author and running
  it; a stored room keeps the pieces people added unless a piece now stands
  where one of them was, which drops theirs.
